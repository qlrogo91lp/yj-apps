## 한 줄 요약

**내가 워치로 점수를 세면, 그 결과가 클럽 대진표에 바로 들어가고, 모두의 폰에 실시간으로 보인다.**

| 영역 | 기능 |
|---|---|
| 정모 운영 | 참석 투표, 정원 초과 대기열, 반복 일정, 캘린더 동기화, 미설치 게스트 링크 초대 |
| 대진 | 자동 매칭 4종(셔플 / 비슷한 실력 / 밸런스 등), 남복·여복·혼복, 고정 페어, 직접 짜기 |
| 랭킹 | ELO, 승점 자동 계산, 리그별 랭킹, 지난 모임 대비 순위 변동 |
| 내 경기 | 클럽 없이도 기록, 상대별 전적, 회고 태그·메모 |
| 커뮤니티 | 게시판, MVP, 카카오톡·인스타 공유 |

**경쟁이 아니라 빈칸이 맞물린다.** CourtMate 는 점수를 세지 않고 경기 뒤에 결과를 입력한다.
Ralli 는 점수를 정확히 세지만 누구와의 경기인지 모른다. Ralli 의 차별점은 **"워치가 결과를 채운다"**
하나이고, CourtMate 의 운영 기능(참석 투표·게시판·일정)은 따라가지 않는다.

기각한 안 — **총무 폰 한 대로 완결되는 대진표**: 서버는 필요 없지만 점수를 세는 사람과 대진표가
연결되지 않아 이 아이디어의 핵심이 빠진다.

## 목표 — 3단계

| 단계 | 내용 | 새로 풀 문제 |
|---|---|---|
| 0. 기반 | Sign in with Apple, 프로필, 보안 규칙 | 계정이 생기면 **계정 삭제**·개인정보 처리방침이 심사 필수 |
| A. 결과 반영 | 대진 생성, 초대 링크, 자동 매칭, 워치에 "내 다음 경기", 경기 종료마다 대진표·순위 갱신 | 딥링크, 매칭 알고리즘, 기록자 선점 |
| B. 라이브 중계 | 진행 중 경기 점수를 포인트 단위로 다른 회원 폰에 | 쓰기 빈도, 코트 네트워크 불안정 |
| C. 워치 공동 기록 | 같은 경기의 워치 여러 대가 하나의 점수를 공유 | **가장 어렵다** — 동시 입력 중복, 폰 경유 지연 |

셋 다 최종 목표다. 첫 프로젝트는 **0 → A** 이고, B·C 는 아래 이벤트 로그 구조만 미리 반영해 둔다.

## 결정 사항 (2026-09-23)

| 항목 | 결정 |
|---|---|
| 백엔드 | **Firebase.** Firestore = 영구 데이터, Realtime Database(RTDB) = 진행 중 경기 점수만 |
| 리전 | Firestore **서울**(asia-northeast3), RTDB **싱가포르**(asia-southeast1, 서울 없음). 글로벌 출시지만 유입이 국내 위주. **리전은 한 번 정하면 못 바꾼다** |
| 서버 로직 | **Cloud Functions 없이 시작.** 순위·승점·ELO 는 결과 기록에서 앱이 계산하고 **DB 에 다시 쓰지 않는다** |
| 점수 모델 | **이벤트 로그** (순번, 누가, 누구에게). 최종 결과는 로그의 합, 중계는 로그 구독, 공동 기록은 로그에 이벤트 추가 |
| 단위 | **클럽 모임**(대진·누적 랭킹 저장) + **번개**(클럽 없이 링크·QR, 당일만, 대진표 미저장) — 같은 경기 구조, 클럽 귀속 여부만 다름 |
| 기록자 | 모임 안에서 **워치를 찬 누구나** (선수가 아니어도). 시작 시 Firestore 트랜잭션으로 선점 |
| 개인 기록 | **Ralli 를 쓰는 참가자 전원**에게 저장. 확정 결과를 각자 앱이 받아 "공유 경기 · 기록자 ○○" 로 넣는다 |
| 워치 통신 | 워치는 Firebase 에 직접 붙지 않는다. **폰이 중계** (기존 `MatchConnectivity` 유지, watchOS Firebase 지원 제한) |
| 미사용 회원 | **이름만 있는 게스트 자리** (아래) |
| 레이팅 범위 | **클럽 레이팅이 공식.** 개인 전체 레이팅은 "참고용"으로만 표시 — 클럽을 넘나드는 비교는 부정확하고 가짜 경기 조작을 막으려면 서버 검증이 필요하다 |

### 게스트 자리 (Ralli 를 쓰지 않는 회원)

- 총무가 닉네임(+혼복용 성별, 선택)만 입력해 대진에 넣는다. 실명·연락처는 받지 않고 총무가 삭제할 수 있다
- 클럽 게스트는 클럽 안에만, 번개 게스트는 그날만 존재한다
- 결과·ELO 는 게스트 자리에 쌓인다. 가입 후 **"이 게스트가 나예요" → 총무 승인**으로 연결해 기록을 이어받는다
- 게스트는 기록자가 될 수 없다. 경기에 Ralli 사용자가 없으면 **총무가 결과를 손으로 입력**한다

### 레이팅 규칙 (Elo 채택 2026-10-27 · 세부 미확정)

공식은 표준 Elo 를 쓴다 — `E = 1 / (1 + 10^((R상대 − R나) / 400))`, `R' = R + K × (S − E)`.
복식 처리·점수 차 반영은 표준이 없어 앱이 정한다.

- **복식** — 팀 레이팅 = 두 사람 평균, 증감은 두 사람에게 같게
- **S = 게임 득실 비율** (6:4 → 0.6). 표준 Elo 의 승패(1/0) 대신. Ralli 는 워치가 센 정확한 스코어를 가진다
- K 는 경기 수에 따라 줄인다 (예: 신규 32 → 안정 16). 시작점 1500 또는 NTRP 자기 신고
- **승점은 레이팅과 나란히** 보여 준다 — 국내 동호회는 승점·조 편성에 익숙하다
- 모든 기기가 같은 순위를 내야 하므로 **규칙에 버전을 붙이고 계산 순서(경기 종료 시각 순)를 고정**한다.
  규칙을 바꾸면 전체 기록을 다시 계산하면 된다

검토한 대안: NTRP(계산식 비공개, 자기 신고 등급으로만) / UTR·WTN(비공개) /
Glicko-2(불확실도 반영, 설명이 어려움) / OpenSkill(팀 경기에 가장 맞지만 Swift 구현 직접)

## 추가 결정 (2026-10-27)

| 항목 | 결정 |
|---|---|
| 우선순위 | **기능 구현이 먼저, 수익화는 보류.** 설계 기준은 서버 운영비 최소화 (아래 요금 구조 절) |
| 레이팅 | **Elo 채택.** 위 추천안이 기준이고 K 값·게스트 초기값·S(게임 득실 비율) 여부는 열려 있다 |
| 안드로이드 | 열린 질문의 ②를 좁혀 채택: **보기 전용 웹** — 클럽 랭킹·경기 기록만, 로그인 없음. 대진표·중계 보기는 나중. 링크를 동호회 단톡방에 공유하는 것이 확산 통로이기도 하다 |
| 클럽 과금 | 클럽 생성·가입·인원 수에는 **과금하지 않는다.** 무료 대체재가 있고, 한 명이라도 막히면 랭킹에 구멍이 난다 |
| 첫 서브 설정 | 경기 시작 전 **첫 서브 팀**(탭 한 번), 복식은 **팀별 첫 서버**(두 번 더)를 받는다. 순서가 A1 → B1 → A2 → B2 로 고정이라 이후는 계산된다. 세트 사이 순서 변경은 드물어 수정만 열어 둔다. 워치에 "이번 게임 서브" 표시(무료) + 나중 서브 지표의 바탕 |
| 응원 이모티콘 | 경기 중 다른 사람이 보낸 이모티콘을 워치에 띄운다 — **푸시 알림**으로 (폰이 잠겨 있으면 워치로 넘어간다). 단 푸시 발송에는 서버 함수가 필요해 **"Cloud Functions 없이 시작"과 부딪힌다** → 서버 함수를 들이는 시점(Blaze 전환)까지 미룬다 |

**워치 통신 보충 — 워치 앱은 소켓을 직접 열 수 없다.** watchOS 의 저수준 네트워킹(소켓·WebSocket)은
오디오 스트리밍 중에만 허용된다 ([TN3135](https://developer.apple.com/forums/thread/717615)). 일반 HTTP 는 된다.
"폰이 중계"라는 위 결정이 선택이 아니라 강제인 이유다.

**B 단계 위험 — 경기 중 폰 앱이 깨어 있지 않을 수 있다.** 지금 Ralli 폰 앱에는 워크아웃 미러링도
백그라운드 모드도 없다 (2026-10-27 코드 확인). 워치가 점수를 보낼 때 잠깐 깨는 구조라, 가방 속 잠긴 폰이
RTDB 연결을 경기 내내 유지한다는 보장이 없다. A 단계(종료 때 한 번 쓰기)는 영향이 없다.
B 를 시작할 때 **워크아웃 미러링(iOS 17+)으로 폰 앱을 경기 동안 살려 두는 방안**을 먼저 검증한다.

### 같은 경기를 여러 워치가 기록했을 때 (제안, 2026-10-27 · 미확정)

**먼저 데이터를 둘로 나눈다 — 서로 보내 줄 것이 없다.**

| 데이터 | 누구 것 | 어디에 | 공유 |
|---|---|---|---|
| 점수·결과 | **경기 것** — 경기당 하나 | Firebase 확정 결과 | 클럽 전원 |
| 운동 기록 (시간·칼로리·심박) | **각자 것** | 각자 HealthKit + 각자 Ralli 기록 | 하지 않는다 |

점수는 경기당 하나만 올라가고, 운동 기록은 각자 자기 워치에 남는다. 내 심박을 남에게 보내거나 남의
칼로리를 받아 올 일이 없다.

**점수 중복 규칙**

1. **경기 ID 가 열쇠** — 대진표(또는 번개 QR)에서 경기가 먼저 만들어지므로 같은 경기의 모든 기록이 같은
   경기 ID 를 갖는다. 지금 폰↔워치 저장 중복 제거에 쓰는 `Match.matchId` 와 같은 방식이다
2. **시작 때 선점** (기존 결정) — 먼저 시작한 워치가 기록자. 늦게 시작한 워치에는 "○○ 님이 기록 중"을 띄우고
   점수 없이 운동만 잰다. B 단계가 되면 그 워치에 실시간 점수를 보여 줄 수 있다
3. **그래도 두 개가 올라오면** (코트 오프라인으로 선점 확인이 안 된 경우) — 확정 결과를 트랜잭션으로 쓴다.
   이미 `완료`면 두 번째는 클럽에 반영하지 않는다
   - 점수가 같다 → 조용히 버린다
   - 점수가 다르다 → 먼저 확정된 결과를 유지하고 "다른 점수 기록 있음"을 표시 → **총무가 고른다**
4. **경기 ID 없이 센 경기**(대진표 밖에서 그냥 워치로 센 경기)는 클럽에 자동으로 붙이지 않는다. 시각·참가자로
   추측하면 엉뚱한 경기에 붙을 수 있다. 개인 기록으로 남고, 원하면 "클럽 경기로 올리기"로 참가자를 직접 지정한다

**내 개인 기록에 남는 모습**

- 내가 기록자 → 지금과 같다 (점수 + 내 운동)
- 내가 참가자 → 확정 결과가 오면 "공유 경기 · 기록자 ○○" 로 저장 (기존 결정). **운동 지표는 확정 결과의
  시작·종료 시각으로 내 HealthKit 을 조회해 붙인다** — 서버를 거치지 않는다. 워치를 안 찼으면 빈칸.
  아래 열린 질문의 "시간 매칭 문제"를 경기 시각 구간 조회로 푸는 안이다 (구간 값 = 종료값 − 시작값 계약과 같은 의미)
- 나도 같은 경기를 따로 셌다 → 같은 경기 ID 라 기록 하나로 합친다. 점수는 클럽 확정값을 쓰고 내 운동 지표는 유지한다

## 흐름

```
[모임 전]  총무 폰
  클럽 → 모임 생성 (또는 번개) → 참석자·게스트 선택 → 자동 매칭
  → Firestore: meetups/{m}/matches/{1..n}  (코트, 팀, status=예정)

[모임 당일]  회원 폰
  모임 화면 진입 → Firestore 대진표 구독 + RTDB 연결
  워치에 "내 다음 경기: 2번 코트, 나·A vs B·C"

[경기 시작]  워치를 찬 누구나 (워치 → 폰)
  Firestore 트랜잭션으로 선점 (status=진행중, recorder=나)
  → RTDB /live/{경기ID} 생성 + onDisconnect 등록

[경기 중]
  득점·취소: 워치 → 폰 → RTDB 이벤트 추가
  관전: 대진표 목록은 /live/{경기ID}/요약 만, 경기를 탭하면 로그 전체 구독

[경기 종료]
  폰 → Firestore 확정 결과 (status=완료, 세트 점수) → RTDB 노드 삭제
  모든 회원: 대진표 갱신 → 순위·승점·ELO 재계산, 개인 기록에 저장
```

**연결은 모임 동안 하나, 구독은 경기마다.** Firebase SDK 는 앱당 연결 하나를 유지하고 그 위에서 경로
구독을 붙였다 뗀다. 모임 화면을 떠나면 `goOffline`.

실패 상황:

- 코트 네트워크 끊김 — 중계는 멈추지만 Firestore 오프라인 쓰기 대기열이 확정 결과를 나중에 올린다
- 기록자 폰 종료 — `onDisconnect` 가 "중계 중단"을 표시, 다른 사람이 이어받는다
- 두 사람이 동시에 시작 — 트랜잭션 선점. C 단계에서는 "기록자 여러 명" + 이벤트 순번으로 중복 제거

## 요금 구조

Blaze = 기본료 없는 후불제. 콘솔에서 결제 계정을 연결하면 즉시 전환되고 **Spark 무료 구간은 유지된다.**
아래 숫자는 대략값 — 도입 시 공식 가격표로 재확인한다.

| | 과금 기준 | 무료 구간 | 초과 |
|---|---|---|---|
| Firestore | 읽기·쓰기·삭제 **건수** | 하루 읽기 5만 / 쓰기 2만 / 삭제 2만 | 10만 건당 읽기 ≈ $0.06, 쓰기 ≈ $0.18 |
| RTDB | 내려받은 **바이트** | 저장 1GB, 다운로드 월 10GB | 저장 GB당 $5/월, 다운로드 GB당 $1 |
| Auth | 월 활성 사용자 | 5만 MAU | — |

- **방 개수·연결 시간은 요금이 거의 없다.** 요금 = 업데이트 수 × 보는 사람 수 × 크기
- 동시 연결 100개 제한은 Spark 에만 있다 (Blaze 는 DB 당 20만)
- 결과 반영: 20명·15경기 정모 ≈ 쓰기 15 / 읽기 300 → 하루 정모 100개 이상 무료
- 중계: 150포인트 × 관전 10명 × 0.5KB ≈ 0.75MB/경기 → 무료 10GB 로 월 약 1.3만 경기.
  **Firestore 로 중계하면 업데이트마다 읽기 건수가 곱해져 비싸다** — 그래서 RTDB 로 나눴다
- 올리기·취소 반복도 과금되지만 사람 손으로는 한 시간 연타해도 약 18MB(≈ $0.02) 수준

**실제 위험은 버그와 공격이다.**

| 원인 | 예 | 막는 법 |
|---|---|---|
| 해제 안 한 리스너 | `onAppear` 마다 구독 추가 → 같은 데이터를 N 번 수신 | ViewModel 생명주기에서 한 번 붙이고 해제 |
| 읽기→쓰기 루프 | 대진표 변경 → 순위 계산 → DB 쓰기 → 다시 변경… | **계산 결과를 DB 에 쓰지 않는다** (결정 사항) |
| 범위 없는 쿼리 | 클럽 전체 경기 구독 | 이번 모임·최근 N 개로 범위 제한 |
| 외부 스크립트 | 앱 밖에서 DB 직접 호출 | App Check + 보안 규칙 |

예산 알림은 첫날부터 건다. **알림은 과금을 멈추지 않는다** — 상한이 필요하면 초과 시 결제를 끊는 함수를 별도로.

중계 트래픽 절감 (비용보다 깔끔한 중계를 위해):

- 취소는 "N번 포인트 취소" 이벤트로 — 전체 점수 재전송 안 함
- 목록 화면은 경기별 요약만 구독
- (선택, 나중에) 1초 묶음 전송 — 실수 후 즉시 취소가 관전 화면에 안 뜨지만 1초 지연

### 서버비 최소화 원칙 (2026-10-27)

목표는 **청구서 0원.** 아래는 *제안*이고, 구현 설계 때 확정한다.

1. **Spark(무료) 요금제로 시작한다** — 결제 수단이 연결되지 않으면 청구 자체가 불가능하다. 한도를 넘으면
   그날 요청이 실패할 뿐이다. "Cloud Functions 없이 시작"(Functions 는 Blaze 필요)과 맞물린다.
   지금 Ralli Firebase 프로젝트(Crashlytics 용)가 어느 요금제인지부터 확인한다.
   **Blaze 로 넘어가는 조건:** RTDB 동시 연결 100 개 제한(B 단계) · 푸시 발송 함수(응원 이모티콘) ·
   무료 한도에 실제로 닿을 때. 넘어가는 날 예산 알림을 건다
2. **건강 데이터는 서버에 올리지 않는다** — Firebase 에는 점수·결과처럼 여럿이 봐야 하는 것만 둔다.
   심박·칼로리는 각자 HealthKit 에 이미 있다 (워치가 `finishWorkout` 으로 워크아웃을 저장한다 —
   `WorkoutCore/WorkoutSessionService.swift`). 분석이 필요하면 각자 기기에서 HealthKit 을 다시 조회한다.
   저장 비용이 없고 건강 데이터 공유에 따르는 개인정보 부담도 없다.
   **주의:** 가이드라인 5.1.3(ii)는 "개인 건강 정보를 iCloud 에 저장하지 말 것"을 요구한다. 범위(CloudKit 개인
   DB 포함 여부 등)가 모호해 [개발자 질문](https://developer.apple.com/forums/thread/844159)이 계속 나온다.
   심박 흐름을 CloudKit 에 새로 쌓지 않는다. 지금 Ralli 가 CloudKit 에 동기화하는 평균 심박·칼로리가 여기에
   걸리는지는 별도 확인 거리
3. **경기 하나 = 확정 쓰기 한 번** — A 단계에서는 포인트마다 쓰지 않는다. 포인트 이벤트 로그는 경기 종료 때
   확정 결과 문서에 같이 담는다 (몇 KB). 나중 분석·B 단계와 같은 로그 구조를 쓴다
4. **랭킹 조회 읽기 건수를 묶는다** — 순위를 DB 에 쓰지 않으니(결정 사항) 랭킹을 보려면 클럽 경기 결과를
   전부 읽어야 한다. 경기 300 개 클럽이면 한 번 보는 데 읽기 300 건 → 무료 하루 5만 건이면 전체 합쳐 하루
   약 160 회 조회에서 막힌다. 확정 결과를 **시즌별 묶음 문서 하나**에도 함께 추가하면 조회가 1~2 건으로 준다
   (문서 상한 1MB, 결과 하나 ~200B → 묶음 하나에 약 5천 경기). 계산 결과가 아니라 원본 결과를 묶는 것이라
   "계산 결과를 DB 에 쓰지 않는다"와 충돌하지 않는다. 쓰기는 경기당 2 건이 된다
5. **웹은 Firebase Hosting 무료 구간 + 기본 도메인**(`*.web.app`) — 도메인 비용도 없다. 웹도 같은 묶음 문서를 읽는다
6. **유료 부가 기능을 쓰지 않는다** — 전화번호 인증(SMS 과금) 대신 Sign in with Apple, 이미지 저장소 없이
   텍스트 데이터만
