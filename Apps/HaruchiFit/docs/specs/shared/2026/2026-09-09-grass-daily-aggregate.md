## 한 줄로

`WorkoutRecord` 들을 **날짜 한 칸씩으로 접는다.** 홈 잔디·기록 달력·통계 연 잔디가

홈·달력·통계 셋이 같은 집계를 쓴다 (로드맵 "순서를 이렇게 잡은 이유"). 화면부터 만들면
셋이 각자 계산하게 되고, 규칙이 갈린 뒤에 합치는 건 훨씬 비싸다.

## 2. 산출물

| 이름 | 정체 | 아는 것 | 위치 | 타깃 |
|---|---|---|---|---|
| `DailyAggregate` | 순수 struct | 아무것도. 값이다 | `Shared/Models/` | iOS + 워치 |
| `GrassAggregator` | 순수 함수 | `Calendar` 와 농도 기준만 | `Shared/Models/` | iOS + 워치 |
| `GrassViewModel` | `@MainActor final class … : ObservableObject` | 위 둘 + 배선 | `iOSApp/Features/Home/` | iOS |

`Shared/` 에 두는 이유는 두 가지다 — 루트 `CLAUDE.md` 가 *"Model이 특정 Feature 전용이어도
그래도 `Shared/Models/` 에 둔다"* 로 정했고, **`Shared/` 가 워치 타깃에도 붙어 있어
`HaruchiFitWatchTests` 에서 그대로 테스트된다.** 하루치엔 iOS 테스트 타깃이 없고,
새로 만들면 타깃 규약 문서까지 따라온다.

```
DailyAggregate
  day: Date              ← 자정으로 정규화된 날짜. 칸의 정체성
  totalSeconds: Int      ← 농도 계산의 입력
  strengthSeconds: Int  ─┐ 홈 "이번 주 운동 구성 바" · 통계 "근력/유산소 비율"
  cardioSeconds: Int    ─┘
  totalCalories: Double? ← 칼로리 기준으로 전환했을 때의 입력
  sessionCount: Int      ← 달력 월 요약 "12회 · 9.2시간" · 통계 세션 카운트 (D2)
```

**농도에 쓰는 건 `totalSeconds` 하나지만 나머지도 같은 한 번의 순회에서 나온다.**
농도만 내는 타입은 Phase 4 의 세 화면 중 둘을 못 먹여서 그때 타입을 다시 고치게 된다.

`GrassViewModel` 은 배선만 한다. **규칙은 전부 `GrassAggregator` 에 있다.**

## 3. 캐시를 영속화하지 않는다

아키텍처 5절은 *"일별 집계 캐시를 두는 편이 낫다"* 고 썼다. **데이터가 0건이던 시점의
추정이라 여기서 뒤집는다.**

- 주 3회 × 3년 = 레코드 약 470건. 홈이 실제로 읽는 건 predicate 로 좁힌 **4개월치 50건 남짓**이다.
  아키텍처가 걱정한 건 *칸 수*(119·371)인데 비싼 쪽은 칸이 아니라 레코드 수고, 그건 훨씬 적다
- **무효화 시점이 이미 넷**이다 (생성·수정·삭제·기준 변경). CloudKit 이 붙으면 "다른 기기에서
  도착한 레코드"가 하나 더 는다. 캐시가 진실과 어긋나면 사용자에겐 "잔디가 틀렸다"로 보이고
  복구 수단이 없다
- 캐시를 `@Model` 로 두면 **CloudKit 스키마에 같이 올라가고 기기 간 충돌 대상이 된다.**
  파생 데이터를 동기화하는 건 손해다

**대신 계산을 `body` 밖에 둔다.** 비용이 작아도 View `body` 안에서 접으면 잔디와 무관한 이유로
(스탯 갱신, 최근 기록 스크롤) 딸려 돈다. `GrassViewModel` 이 `@StateObject` 로 살아 있으면
`body` 가 몇 번 재평가되든 결과는 배열 읽기다.

> 이 스토어는 **성능 캐시가 아니라 계산의 자리**다. 나중에 프로파일링이 요구하면
> 같은 순수 함수 위에 캐시를 얹을 수 있다 — 화면 코드는 안 바뀐다.

## 4. 집계 규칙

### 4.1 하루의 경계 — 시작 시각

23:40 에 시작해 00:30 에 끝난 50분 세션은 **전부 시작한 날 칸**에 들어간다.

날짜별로 쪼개지 않는 이유: 통계가 세션 카운트 기준(D2)이고 기록 목록도 세션 단위다.
한 세션을 쪼개면 **잔디만 다른 수를 갖는다.** "어제 밤에 운동했다"는 인식과도 맞는다.

정규화는 `Calendar.current.startOfDay(for: record.startedAt)`.

**타임존은 `.current`** — 해외에 나가면 과거 칸이 한 칸 움직여 보일 수 있다. 기록 시점의
타임존을 저장하는 대안은 모델에 필드를 늘리는 값에 비해 얻는 게 없다. v1 은 이대로 간다.

### 4.2 시간 값 — `totalSeconds`

세그먼트 합이 아니라 레코드의 `totalSeconds` 를 쓴다. 수동 기록과 HealthKit import 기록은
세그먼트가 없을 수 있고, `totalSeconds` 는 **모든 소스에 반드시 있다.**

선행 작업 이후 이 값은 **일시정지를 뺀 시간**이다.

### 4.3 농도 4단계

| 단계 | 조건 |
|---|---|
| **0 (빈 칸)** | 그날 레코드가 **없음** |
| 1 | ~30분 |
| 2 | 30분 이상 ~ 60분 미만 |
| 3 | 60분 이상 ~ 90분 미만 |
| 4 | 90분 이상 |

D-M6 확정값에 **0단계를 채웠다** — 스펙은 1~4단계만 정의했었다.
경계는 **이상/미만**으로 못박는다. 정확히 30분은 2단계다.
레코드가 하나라도 있으면 아무리 짧아도 **1단계 이상**이다.

### 4.4 기준 값이 없으면 1단계

제품 스펙 D4 의 *"수동 기록(HealthKit 값 없음)은 최소 농도 fallback"* 은 두 가지로 읽힌다.
**괄호를 조건으로 읽는다.**

> 그날의 기준 값(시간 또는 칼로리)이 **없거나 0이면 1단계.** 있으면 컷 표대로.

`source == .manual` 이면 무조건 1단계로 읽으면 틀린 값이 나온다 — 08 수동 기록은 사용자가
**시간을 직접 입력**한다 (스펙 08절). 90분을 손으로 넣었는데 1단계로 찍히면 그건
fallback 이 아니라 버그다. 반대로 **칼로리 기준으로 전환하면** 수동 기록엔 칼로리가 없으니
그때 1단계로 떨어지는 게 맞다 — 괄호가 가리키는 게 정확히 그 상황이다.

이렇게 쓰면 **농도 계산이 `source` 를 아예 안 본다.** 칼로리 기준을 나중에 붙일 때 분기가
하나도 늘지 않는다.

### 4.5 반영 범위 (D-M5)

*근력·유산소로 분류되는 워크아웃만 잔디에 반영한다.* **지금은 자동으로 만족한다** —
레코드가 워치 세션밖에 없다.

**집계기는 필터를 갖지 않는다.** 들어온 건 다 센다. 거르는 일은 #2 HealthKit import 가
매핑 표로 **입구에서** 한다. 두 곳에서 거르면 규칙이 갈린다.

## 5. 데이터 흐름

```
@Query(기간 한정)  ──▶  GrassViewModel.rebuild(from:)  ──▶  @Published days  ──▶  View
   SwiftData                 GrassAggregator.fold                배열 읽기
```

View 가 `@Query` 로 읽어 ViewModel 에 밀어넣는다. SwiftData 는 **컨테이너 단위로** 변경을
전파하므로, 워치 기록을 저장하는 `iOSApp.save(_:)` 의 별도 `ModelContext` 가 써도 `@Query` 가
갱신된다. **이미 도는 경로다** — 지금 임시 `ContentView` 가 그렇게 워치 기록을 받아 그리고 있고
실기기 검증을 통과했다.

`@Query` 는 기간을 좁혀 읽는다. 홈은 4개월치면 충분하다.

### 갱신이 언제 일어나나

`records` 는 `[WorkoutRecord]` 이고 `PersistentModel` 은 **동일성(`persistentModelID`)으로**
비교된다.

| 상황 | 갱신 | 이유 |
|---|---|---|
| 워치 기록이 도착해 저장됨 | ✅ | 원소가 늘었다 |
| 기록 스와이프 삭제 | ✅ | 원소가 줄었다 |
| CloudKit 이 다른 기기 기록을 밀어넣음 | ✅ | 원소가 늘었다 |
| **HealthKit import 가 기존 기록을 갱신** | ✅ | `PersistenceService.upsert` 가 **지우고 새로 넣는다** |
| 04 상세에서 메모·부위 태깅 편집 | — | 잔디 입력이 아니다. 무관 |
| **08 수동 기록에서 시간·날짜 편집** | ❌ | 원소 집합이 그대로다 |

**구멍은 마지막 하나뿐이고 그걸 여는 화면이 아직 없다.** `refresh()` 를 공개 메서드로
열어두기만 하고, **Phase 5 의 08 수동 기록이 편집 저장 직후 그것을 부른다.**

### 당겨서 새로고침은 지금 붙이지 않는다

지금은 당겨봐야 로컬 레코드를 다시 접는 것뿐이라 **99% 같은 결과**가 나온다.
아무 변화가 없는 컨트롤은 "고장난 것 같다"는 인상만 준다.

**#2 HealthKit import 가 붙으면 `.refreshable` 을 홈에 단다** — 그때는
*"지금 건강 앱에서 다시 가져와"* 라는 **실제로 할 일이 있는 동작**이 된다.
D-M4 가 백그라운드 배달을 안 쓰기로 해 동기화 시점이 "포그라운드 진입" 하나뿐인데,
사용자가 직접 당길 수 있는 두 번째 시점이 생기는 건 값어치가 있다.

## 6. #2 HealthKit import 가 지켜야 할 불변조건

**`healthKitUUID` 가 이미 있는 레코드는 import 가 건드리지 않는다.**

건드리면 이렇게 된다 — 워치로 저장한 기록의 `totalSeconds` 는 앱이 잰 값(정지 제외)인데,
같은 워크아웃의 `HKWorkout` 은 HealthKit 이 잰 값이다. `upsert` 가 기존 레코드를 지우고
새로 넣으므로 **과거 잔디 농도가 소급해서 바뀐다.**

import 의 목적은 *다른 앱이 저장한 워크아웃*을 데려오는 것이지(아키텍처 4.1) 우리가 이미
세그먼트까지 갖고 있는 기록을 다시 쓰는 게 아니다. **#2 플랜은 이 문서를 근거로 삼는다.**

## 7. 임시 확인 화면

`iOSApp/ContentView.swift` 의 리스트를 **잔디 그리드 하나**로 교체한다.

- 17주 × 7일 그리드. 단색 오렌지 4단계 + 빈 칸
- 칸을 탭하면 그날 값을 텍스트로 (분 · 세션 수 · 근력/유산소)
- **제품 화면이 아니다.** Phase 3 탭 셸이 대체한다. 지금 파일에 달린 주석의 성격을 그대로 잇는다

애니메이션·스와이프·스탯은 넣지 않는다. **농도 컷이 실제 데이터와 맞는지 눈으로 보는 것**이
이 화면의 유일한 목적이다.

## 8. 검증

### 유닛 테스트 (`HaruchiFitWatchTests` — 순수 함수)

- 같은 날 30분 + 40분 두 세션 → **한 칸 70분 · 3단계 · `sessionCount == 2`** (D3)
- 23:40 시작 50분 세션 → **시작한 날 칸에 50분 전부**
- 컷 경계 — 정확히 30분은 2단계, 29분59초는 1단계, 90분은 4단계
- 1초짜리 레코드 → **1단계** (0단계로 떨어지지 않는다)
- 레코드 없는 날 → **칸이 없다** (0단계)
- 기준 값이 0이거나 없음 → **1단계** (4.4)
- 세그먼트가 없는 레코드 → `strengthSeconds == cardioSeconds == 0`, `totalSeconds` 는 그대로
- 근력 20분 + 유산소 10분 섞인 세션 → 종목별 초가 갈려 담긴다
- 빈 입력 → 빈 결과. 크래시 없음

### 눈으로

- 임시 화면에서 실기기 기록의 농도가 실제 운동 시간과 맞는지
- 워치에서 운동을 마치면 **폰을 켜 둔 채로도** 칸이 채워지는지 (`@Query` 전파)
